# ROS 2 的两跳消息和回调计时

Eclipse Trace Compass 的 ROS 2 样例在同一台主机上运行了三个进程。源节点每 5 ms 向 `/topic_a` 发布，中继节点在订阅回调内向 `/topic_b` 发布，末端订阅该主题。这里测到的是软件执行时序。该实验没有无线链路或物理执行器读数。[文件版本、权限与实验启动描述](sources.json)

从 99,338 条运行事件中，按主题和 DDS 源时间戳，配出了 **1,986 条贯穿两跳的消息链**。中继发布还须处于匹配到的输入回调和同一线程内。以首次 `rcl_publish` 到末端回调开始计，时延中位数为 **0.458095 ms**，95% 分位数为 **0.702485 ms**，最大为 **45.537944 ms**。14 条超过源节点的一个定时周期，其中 9 条出现在最初 10 条完整链中。[1,986 条逐链分解](matched-chains.csv) · [时延统计](timings.csv)

观测范围影响计数。第一跳有 2,031 次写入和 1,986 次对应的成功接收，未配对的 45 次写入位于匹配区间两端，前端 5 次、后端 40 次。第二跳有 40 次成功接收缺对应写入，全部晚于最后一次配对接收。文件没有给出缺失原因，无法据此估算丢包率。[事件计数和边界](trace-counts.csv)

ros-tracing 公开的 ping–pong 样例则只有回调侧计时和初始化信息。248 个事件中出现 30 次“定时器回调 → 对端订阅回调 → 本端订阅回调”的有序组合，首尾开始时刻的间隔中位数为 **1.6185805 ms**。样例缺少带消息标识的发布和接收事件，只能报告这个时间间隔，不能把它当成逐包往返时延。[两个样例的字段与来源](sources.json)

复算需要 Python 3 和 Babeltrace 2。运行 `python recompute.py OUTPUT CACHE` 会按固定版本下载 Git 对象，核对 18 个源文件的 Git blob，再生成三张 CSV。汇总使用纳秒。百分位数采用最近秩定义。[输入文件校验单](trace-blobs.json) · [查询与排除记录](search.json)
