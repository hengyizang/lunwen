## P0：必须先解决的关键缺口

### P0-01：模型作者能够改写执行器记录

依据：[scripts/api_orchestrator.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/api_orchestrator.py) 的 `safe_target` 和 `apply_bundle`。

隔离复现调用真实写入函数，发现作者产物包可以写入 `experiments/registry.jsonl`、实验目录中的 `metrics.csv` 和 `stdout.txt`。`state/run.json`、受控文献检索日志，以及实验目录中的 `run.json` 正确受到保护。

这证明实验记录写入边界不完整，不证明已伪造正式结果或成功绕过全部 G4/G5。实验门禁读取登记表及文件哈希；如果模型可以同时编写某些输入记录和结果文件，哈希一致本身不能证明实验确实执行。

应修补：只让受控实验执行器写入登记表、执行日志和指定结果输出，建立执行回执和结果来源验证。模型可写计划、实验代码、解释及论文草稿，但不能把自行生成的文本登记为执行事实。

验收：作者对执行器记录的写入全部拒绝；通过真实执行器产生的成功、失败和负结果均可校验；没有执行回执的结果不能进入证据目录或通过关卡。

### P0-02：含糊超时后的自动重试可能漏记费用

依据：[scripts/ai_providers.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/ai_providers.py) 的 `_request`；[scripts/model_runtime.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/model_runtime.py) 的 `call`。

底层请求对超时、连接错误及部分响应解析错误自动重试，未提供已验证的幂等保证。上层一次预留最终只按返回成功的请求用量结算。

模拟“首个请求超时、第二个成功”：观察到两次传输尝试、没有幂等标识、单一预留被最终返回用量结算、没有保留未解决请求。首个请求可能已在供应商侧生成并收费；本次模拟没有实际供应商费用，也没有证明真实超支。

应修补：对可能已计费的含糊失败停止盲目重试，保留预留并对账；或者使用该供应商明确支持并验证的幂等请求。每个需重新发起的生成请求必须有独立且保守的计费记录。

验收：覆盖请求已被接受但响应丢失、无用量回执、成功重试及余额临界情况；未对账的潜在费用不能因下一请求成功而消失，累计 300 元上限保持可核查。

### P0-03：当前云端循环没有调用真实实验或数据获取执行器

依据：[scripts/cloud_job.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/cloud_job.py) 的 `cycle_command`；`api_orchestrator.run_cycle`；[scripts/experiment_runner.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/experiment_runner.py) 的 `execute`。

云端 cycle/continuation 调用的路径是模型规划、作者产物、初次批评、修订和最终批评。到 `experiment-execution` 阶段只刷新已有登记表的证据目录，没有实际调度实验执行器；模型作者没有 shell 执行工具，写出代码不代表执行代码。当前云端动作也没有接入受控数据下载和实验执行动作。

实验执行器本身已有批准的 G3 计划和预算哈希、输入检查、固定 Docker 镜像摘要、随机种子、超时和失败记录等机制。这是未接入主流程的能力，不是模块不存在。

应修补：按阶段接通合法数据获取、受控实验、结果校验及后续证据刷新，复用现有执行器。检查已完成运行，避免续跑重复付费或只保留有利结果；正式项目仍须在真实 G3 人工批准后执行。

验收：在隔离验收项目完成一条云端数据获取—批准计划—真实实验—负结果保留—证据绑定路径，再验证正式项目的受批准路径。不得用模型生成的数字代替执行。

### P0-04：跨云任务检查点会遗漏代码及证据

依据：`cloud_job.safe_file`、`selected_files` 及其持久化、恢复和结果 ZIP 调用。

当前仅保存指定目录与扩展名，单文件限 2 MB，总量限 15 MB；`.py`、`.yaml`、`.xml`、`.parquet` 等不在扩展名集合，`results` 不在顶层目录集合。Git 状态分支和结果 ZIP 都使用同一筛选器。

实际隔离复现：登记表、手稿 `.tex` 和报告 `.csv` 被保存；实验脚本 `.py`、配置 `.yaml`、文献来源 `.xml`、处理数据 `.parquet` 及图形渲染脚本 `.py` 被静默遗漏。下一次全新云任务可能保留计划和哈希，却丢失运行所需文件。`api_runs` 和缓存也没有通过该结果快照保留，跨任务回溯与复用不足。

原始、私密及大型数据不进 Git 是正确约束。应修补小型安全代码、配置与来源文件的检查点，并为授权的大型/私密数据和输出建立外部存储、哈希清单及恢复流程。不能把所有原始数据直接纳入 Git 来解决问题。

验收：至少两个独立云 runner 之间恢复完整的批准输入、脚本、配置、证据和结果；逐项核验哈希。需要继续使用而不能持久化的文件必须显式报错或有验证过的重建方法，不能静默丢弃。

### P0-05：选题检索没有产生 G1 要求的受控文献回执

依据：`api_orchestrator.discover_context`；[scripts/literature_evidence.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/literature_evidence.py) 的 `execute_search`；[scripts/researchctl.py](https://github.com/hengyizang/lunwen/blob/111c0416a0565d7dc8bbb0bd2e3a3b9a21023774/scripts/researchctl.py) 的 G1 检查。

主循环使用旧 `literature_discovery.discover` 获取元数据上下文，未调用记录原始响应、归一化元数据、`evidence/search-log.jsonl` 和 `literature-api-ledger.jsonl` 的受控检索模块。数据集自动发现写出的另一种日志不能替代文献检索回执。作者禁止写受控检索日志是正确保护，不能解除该保护来弥补接线。

模拟检索成功后，主流程返回了元数据，但没有建立 G1 必需的文献检索日志。旧 OpenAlex 检索也没有读取已配置的 API key，且其失败可能在 Crossref 搜索开始前中断发现；更完整的文献证据模块尚未成为该循环入口。

应修补：调用已有受控检索模块，保存查询、日期、数据库、原始来源和筛选记录，再衔接正反向引文追踪、合法全文获取、阅读记录和来源范围确认。

验收：实际检索回执与文件哈希可重算；某一来源失败时有明确降级记录；“没有检索到”不被表述成“已证明新颖”；确认源文后才能把引用用于科学论证。

## 修补顺序与完成判据

1. 先封闭模型对实验事实的写入权限，并修补含糊失败的计费与对账。

后续更新必须通过实际运行回执和验收逐项关闭发现；这份报告的发布只保存审计结论，没有关闭任何代码缺口。
