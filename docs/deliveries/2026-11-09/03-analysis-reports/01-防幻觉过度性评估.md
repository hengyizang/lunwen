# 防幻觉 / 防造假：是否做得太过了？

> 针对 `D:\ad\lunwen`（Doctoral Research OS v2.3.0）的设计权衡评估
> 依据：12 份逐文件精读报告 + 全仓定量统计（2026-11-09）

---

## 结论先行

**是，明显过头了，而且已经从「防止造假」异化成「证明自己没做事」，产生了反效果。**

但要先把话说准：问题不在「要不要防」，而在**防的粒度、成本由谁承担、以及它优化的到底是什么**。防编造引用、防伪造实验结果、防自动投稿，对一套面向学位与期刊的系统是刚需。可这套系统把同样的强度铺到了每一个中间态、每一个观察值、每一份文档上，结果变成了：**拒绝的逻辑远多于产出的逻辑，可辩护性取代了科研产出，成为系统实际优化的目标。**

最直白的证据：全仓 **4,730 处 `raise`，对应 688 处实际写文件/导出语句（6.88 : 1）**；项目停在 G1 未批准，六篇论文全是空模板，零实验、零结果。一套防止造假的装置，成功防止了任何东西被产生。

## 二、过度带来的四种真实代价

### 1. 信号稀释：当所有字段都是 False，False 就不再携带信息

226 种「未验证」键名看似严谨，实际效果是把「未知」「未做」「不认可」「需人工」「仅供建议」揉成一堆同义的 `False`。读报告的人无法一眼分辨哪些是**尚未开始**、哪些是**已做但未通过**、哪些是**刻意不作判断**。信息论上，这是典型的冗余编码——标记越多，单个标记的信息量越接近零。最后所有人（包括系统自己）只能靠一句总免责「工程验收不代表科学有效」兜底，而这句话在 docs 里出现了 354 次。

### 2. 成本爆炸：改一处要同步四层

一次字段调整要同时改 Python 逻辑、JSON Schema、合成夹具的硬编码期望值、以及文档里的免责说明。12 份精读报告反复出现同一类抱怨：硬编码阈值跨文件重复（`300/500/600/725/1200 CNY`、0.85、24 篇、8/8.5 分、11 个 CI 检查名）、同名函数跨模块签名各异、模型 ID 与路由在多个文件里各写一份。复杂度本身开始制造不一致——预算 300 vs 500、费用 0 vs 3.889 元、`paper-qa==2026.08.12` vs `2026.8.12`、`stages.json` 仍写死 Q2/IF>1.0 而文档说已降级。**越想防错，越容易出现新的错。**

### 3. 责任真空：每个判断都推出去，最后没人接

系统把每一处判断都标成「需人工决定 / 需真实证据 / 需独立审查」，逻辑上无懈可击；但 `projects/my-phd/state/run.json` 显示 **G1、G2 从未人工批准**，`g1-human-screening-sheet.csv` 757 行的 4 个人工字段 100% 为空，`continuation-status.should_run=false`（"automatic research not started"）。于是形成一个死锁：**系统不肯替人决定，人也没被真正要求决定，流程就永远停在 G1**。护栏把责任转移得干干净净，也把进展转移得干干净净。

### 4. 自相矛盾：最强调「不可伪造」的系统，审批记录却可由夹具伪造

精读里最反讽的一组发现：

- `acceptance_scope.py` 展示用 `DR_OS_CLOUD_EXECUTOR=1` + `seal_approval` 就能生成「人工批准」记录；云闸门仅凭可伪造的环境变量判定。
- `cloud_human_controls.execute` 未传 `owner_authorization` 时，以 `verified=False` 的「本地声明」身份记录人工决定；`actor` / `approved_by` 多为字符串自报、无签名。
- 测试里的共享夹具 `sealed_run` / `seal_review` 会构造「G3 批准 + 成功回执 + 独立审查通过 + 人工确认」的**合成替身**，被 20+ 文件复用。
- `artifact_hash` 刻意排除 `state/`、`experiments/runs/`、`raw/`，形成哈希绕过面。

也就是说：复杂度堆得越高，真正需要保护的少数几个边界反而越容易被绕过。**护栏的覆盖面与有效性不是正相关。**

## 三、为什么会走到这一步（值得警惕的模式）

从提交历史（#115 → #174，21 个提交）和文档措辞看，很像一条「免责军备竞赛」路径：每发现一个可能被质疑的点，就加一层检查 + 一个 schema + 一份验收报告 + 一句免责声明，而不是判断这个风险是否真会发生。AI 辅助生成代码尤其容易放大这个倾向——模型倾向于**追加免责与校验**来显得可靠，而不擅长**删掉不必要的分支**。结果是「新增能力」的提交里，大半是新的审计层与占位标记，`retired` / `not_assessed` 越堆越多，却没有一处被真正清理。

判断标准其实很简单：**好的护栏应该让真实工作更容易完成，而不是更难。** 如果一套流程运行一年（10 月至今）还停在 G1、零篇论文、零实验，那么无论它的证据链多严密，都该重新审视护栏本身，而不是再加一层。

## 四、分层处置建议

### A. 必须保留（真正防造假的核心，约 6 条）

1. G1 博士选题、G2 逐篇选题的**真人决定**记录；
2. **绝不自动投稿**，投稿包只产出本地 ZIP；
3. 来源与产出文件的**哈希绑定 + 不可变 ledger**（但不必 88% 模块都算，收敛到产出边界即可）；
4. **累计预算**与每次尝试（含失败/负结果）计费；
5. **角色隔离**（Claude 只读规划/批评，非 Claude 写持久产物）与输出 provenance；
6. 真实外部调用前的**来源、模型身份、许可/访问控制**校验。

这几条都作用在「不可逆且外部可见」的边界上，成本合理、收益明确。

### B. 应当收敛（把噪音压回信号）

| 现在 | 建议 |
|---|---|
| 226 种 `*_verified` 键名 / 748 次 | 收敛为一个 `EvidenceStatus` 枚举：`unknown / claimed / source_bound / reproduced / human_approved`，最多 5 个值，全仓共用 |
| 69 个 JSON Schema | 按 G0–G5 六阶段合并，共享基础类型 |
| docs 里 354 处重复免责 | 集中到 `AGENTS.md` + 一份 `POLICY.md`，其余文档引用而不复述 |
| 88% 文件计算 sha256 | 只在「产物落盘 / 冻结 / 对外交付」三处算，内部中间态用状态枚举 |
| `scripts/*acceptance*.py`（10+）与 docs/acceptance 9 份 | 合并为一份机器可读的验收矩阵，删掉重复报告 |
| 16 个 CI 工作流 + 156 项 checklist | 保留阻断项，把观察项从「检查」降为「报告」 |

### C. 应该删除（占位与自我重复）

- 48 处 `retired` / 46 处 `not_assessed` 对应的模块：H/AD/CFH 机械扫描、humanization action、统计水印检测、`calibration_analysis` 的 `NOT_CALIBRATED` 锁、GPT Image fail-closed 路径、未接线的 `reusable_reader`；
- 把「分数 / Q1/Q2 / IF / 期刊 AI 政策」降级为观察项后，仍保留的全套检查代码；
- 合成夹具里能伪造「人工批准 / 独立审查通过」的路径，改为强制真实签名或显式 `synthetic` 标记且不可进入闸门；
- 硬编码的未来型号（`gpt-6.1-sol` / `claude-opus-5-5` / `deepseek-v4.1-flash`）与互相矛盾的阈值（8/8.5 分、Q2、IF>1.0）。

### D. 流程上更该优先做的事

1. **先跑通一次真实的 G1→G2 人工决策和一次真实付费模型周期**，用真实结果校准哪些护栏真被触发过；
2. **按「实际触发过的拒绝」来删护栏**——从没触发过的 `raise` 分支、占位检查、验收报告直接删，比按设计文档删更可靠；
3. 把目标从「可辩护」改回「可完成」：每加一条护栏，要求同时说明它防的是哪一个**已发生过或高概率**的具体失效，否则不加。

## 五、一句话评价

这套系统像一份**永远在准备接受审计、却从未提交的研究档案**：它把「不撒谎」做成了架构级能力，代价是把「做事」也一起挡在了门外。防造假该守在少数几个不可逆边界上，而不是渗进每一次函数调用。当前最需要的不是再加一层检查，而是**删掉一大半，然后真的开始跑一次**。
